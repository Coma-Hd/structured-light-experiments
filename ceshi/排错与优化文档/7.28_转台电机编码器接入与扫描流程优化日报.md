## 2. 电机与编码器接入

### 2.1 原流程问题

原来的转台采集程序不读取编码器，每帧角度由下式估算：

```text
angle = start_angle + elapsed_time × assumed_angular_velocity
```

该方法要求转台严格匀速，无法反映：

- 开环速度波动；
- 电机丢步；
- 实际转速与设定转速偏差；
- 加减速过程；
- 串口或系统调度造成的时间误差。

### 2.2 新流程

新增：

```text
src/turntable_motor.py
```

采集程序现在直接完成：

```text
连接 COM 口
→ hello 验证 HC32 固件
→ motor run 启动电机
→ 定时刷新 1 秒控制租约
→ 读取 axis status
→ 获得连续 actual_mdeg
→ 达到目标实测角度后停止
→ 异常时 motor off + stop
```

串口参数固定为：

```text
115200 8N1
```

固件身份应答：

```text
Hello HC32F448 position control
```

### 2.3 每帧编码器角度

编码器返回减速器输出轴连续展开角度：

```text
actual_mdeg
```

单位为 `0.001°`，跨越单圈零点后不会清零。

相机帧和串口回复都使用 `perf_counter` 单调时钟。每帧角度由相邻两个编码器样本线性插值：

```text
frame_angle =
    first_frame_angle
    + interpolated_actual_mdeg_difference / 1000
```

因此点云重建直接使用实测角度，不再对实时角速度进行二次积分。

## 3. 实际联调问题与修复

### 3.1 COM10 首次握手失败

首次运行出现：

```text
COM10 未返回 HC32 握手应答
```

直接串口探测后能够收到正确的 HC32 应答，说明：

- COM10 正确；
- 115200 波特率正确；
- 固件正常；
- 首次失败属于端口刚打开时的瞬时问题。

实际使用时应关闭原电机 GUI 和其他串口工具，避免 COM10 被占用。

### 3.2 电机速度无法稳定

目标速度为 `1 deg/s` 时，编码器实测约为：

```text
-0.85 ～ -1.18 deg/s
```

负号来自编码器原始方向与控制方向定义相反，不代表电机反转。

由于当前控制是开环控制，速度不稳定是客观情况。扫描已经使用编码器位置，因此没有必要把“速度达到并保持目标值”作为开始条件。

修正后：

- 只要求编码器检测到持续运动；
- 不再要求实测速度接近设定值；
- 自动识别编码器符号；
- 自动把编码器角度统一到用户指定的正负方向；
- 速度波动仍会被每帧实测角度正确记录。

### 3.3 固件偶发拒绝运行命令

采集中出现过：

```text
Motor run REJECTED reason=range duty=700 step_us=1800
Motor run REJECTED reason=direction_change_stop_first
```

对于 `1 deg/s`，正确值应为：

```text
step_us=18000
```

固件偶发收到 `1800`，以及偶发识别成反方向，说明 20 Hz 状态查询下，DAPLink 串口链路或固件命令处理发生了丢字符。

修正：

- 编码器状态查询由 20 Hz 降至 10 Hz；
- 电机控制租约仍按 250 ms 刷新；
- 单次错误应答不立即终止；
- 连续拒绝 3 次才判定为真实故障并安全停机。

最新一次失败采集只得到：

```text
22 张图
43.053° 角度覆盖
```

该数据不足以完成要求至少 `90°` 的正式转轴标定，需要修复后重新采集。

## 4. 为什么需要标定转台旋转轴

编码器只能告诉程序“转了多少度”，不能告诉程序物体在相机坐标系中“绕哪条三维直线旋转”。

转轴标定求得：

```text
C：转轴上的一点
n：转轴方向
```

每帧激光点通过下式回到第一帧坐标系：

```text
P_reference = C + R(n, -θ) · (P_current - C)
```

如果不标定转轴，而是假设物体绕相机原点或理想竖直轴旋转，会造成：

- 点云偏心；
- 尺寸随角度周期变化；
- 表面扭曲；
- 不同角度无法正确融合；
- 0°/360°出现错缝或双层。

移动相机、转台本体或改变两者相对安装后必须重新标定转轴。



后续又调整为：

- 即使质量不合格，也输出并保存完整计算结果；
- 如果数据不足以拟合转轴，也输出有效位姿、角度覆盖和失败原因；
- 不合格时仍返回失败状态，防止误用于正式扫描。

## 6. 支持任意扫描角度

正式重建不要求每次必须旋转 `360°`。

可通过：

```powershell
-MaxRotationDeg 120
```

只采集需要的 `120°` 范围。

后续流程会自动使用本次实际角度范围：

```text
3_draw_check.ps1
→ 在实际范围内均匀选择关键帧

4_rebuild.ps1
→ 按本次 angles.csv 重建局部角度点云
```

只有检查整圈首尾闭合时才必须扫描 `360°`。

## 7. 相机启动预热

实际采集中发现，相机刚打开时曝光和增益尚未完全生效，前几帧亮度不稳定。

现在设置相机参数后默认读取并丢弃前：

```text
5 帧
```

然后才连接并启动电机，避免不稳定图像进入采集。

可通过以下参数调整：

```powershell
-WarmupFrames 10
```

## 8. Laser Check 蓝线断裂

### 8.1 问题表现

上传的四张 Laser Check 中，真实蓝线基本连续，但红色中心点只有零散片段：

```text
原提取数量约 38～55 点
```

### 8.2 根本原因

转台配置仍使用旧参数：

```yaml
score_mode: blue_gated_intensity
max_saturated_width_px: 4
```

但当前相机把激光亮核拍成约 `10～18 px` 的饱和白色区域，并且当前激光平面标定使用的是新的 `blue_guided_intensity` 参数。

这造成：

1. 白色激光核心没有蓝色差，旧门控无法覆盖；
2. 饱和宽度超过 4 px 后被质量过滤器删除；
3. 转台提取参数与激光平面标定参数不一致。

### 8.3 修正

转台配置已与激光平面标定配置对齐：

```yaml
score_mode: "blue_guided_intensity"
blue_gate_threshold: 5
blue_gate_expand_px: 5
max_width_px: 90
max_saturated_width_px: 20
min_secondary_segment_points: 4
max_secondary_segment_offset_px: 20.0
```

修正后，同样四张图片的提取数量达到：

```text
94～101 点
```

新的方法先利用蓝色光晕定位激光邻域，再在邻域内寻找最亮的白色核心，适合当前相机图像。
